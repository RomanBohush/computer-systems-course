## Lab 1

**Представлення даних у пам'яті комп'ютера.** Код: `labs/lab01-data-representation/`.

### 1. Прогнози (записані до запуску)

- Розміри типів: char 1, short 2, int 4, long 8, long long 8, float 4, double 8, void * 8
- Бітове представлення -1 у int8_t: 11111111
- 255 + 1 у uint8_t: 0
- Порядок байтів 0x12345678 (A: 12 34 56 78 чи B: 78 56 34 12): Варіант B

### 2. Розміри типів (types.c)

```
char:      1 bytes
short:     2 bytes
int:       4 bytes
long:      8 bytes
long long: 8 bytes
float:     4 bytes
double:    8 bytes
void *:    8 bytes
```

| Тип | Байти | Біти |
|---|---|---|
| char | 1 | 8 |
| short | 2 | 16 |
| int | 4 | 32 |
| long | 8 | 64 |
| long long | 8 | 64 |
| float | 4 | 32 |
| double | 8 | 64 |
| void * | 8 | 64 |

- Чи всі типи займають однакову кількість пам'яті? Ні, розмір залежить від типу та платформи.
- Скільки бітів займає int? 32.
- Розмір void *? 8 байтів.
- Що це говорить про архітектуру? Вказівник зберігає адресу, тож 64-бітний вказівник означає 64-бітну архітектуру (x86-64) з 64-бітним адресним простором.

### 3. Decimal / Hexadecimal / Binary (representations.c, binary.c)

| Decimal | Hexadecimal | Binary |
|---|---|---|
| 10 | 0xA | 00001010 |
| 65 | 0x41 | 01000001 |
| 127 | 0x7F | 01111111 |
| 255 | 0xFF | 11111111 |
| 256 | 0x100 | 100000000 |
| 1024 | 0x400 | 10000000000 |

Вивід binary.c:

```
Decimal:   0  Hex: 0x00  Binary: 00000000
Decimal:   1  Hex: 0x01  Binary: 00000001
Decimal:  10  Hex: 0x0A  Binary: 00001010
Decimal:  65  Hex: 0x41  Binary: 01000001
Decimal: 127  Hex: 0x7F  Binary: 01111111
Decimal: 128  Hex: 0x80  Binary: 10000000
Decimal: 255  Hex: 0xFF  Binary: 11111111
```

Чому 65, 0x41 і 01000001 однакові? Це різні записи одного значення в системах числення з основами 10, 16 і 2. Комп'ютер зберігає лише біти, а десятковий та шістнадцятковий запис потрібні людині (64 + 1 = 65; 4*16 + 1 = 65).

Чому print_binary починає з біта 7? Біт 7 старший. Число записується зліва направо від старших розрядів до молодших, тому перевірку починають зі старшого біта, інакше число вивелося б задом наперед.

### 4. Символи (characters.c)

| Character | Decimal | Hex |
|---|---|---|
| A | 65 | 0x41 |
| B | 66 | 0x42 |
| a | 97 | 0x61 |
| 0 | 48 | 0x30 |
| 9 | 57 | 0x39 |

Що зберігається в `char c = 'A';`? Число 65 (байт 01000001). Літера A з'являється лише коли код інтерпретується за таблицею ASCII, наприклад при виводі через %c.

### 5. Signed та unsigned (signed_unsigned.c)

```
int8_t:  -1  hex: 0xFF
uint8_t: 255 hex: 0xFF
```

Очікуване представлення -1: 11111111 (двійковий додатковий код: 00000001 -> інверсія 11111110 -> +1 = 11111111).

Як 11111111 може бути і 255, і -1? Біти самі не мають значення. Як uint8_t усі 8 бітів значущі і виходить 255, як int8_t старший біт є знаковим і виходить -1. Значення визначається типом, тобто способом інтерпретації.

### 6. Межа unsigned (overflow.c)

Прогноз: 255 + 1 = 0.

```
value = 254
value = 255
value = 0
value = 1
```

Результат збігається з прогнозом: після 255 значення стає 0, потім 1. Число 255 це 11111111, максимум для 8 бітів. Сума 256 потребує 9 бітів (1 00000000), а змінна має лише 8, тож дев'ятий біт відкидається і лишається 00000000. Беззнакове значення обертається за модулем 256. Це стосується лише unsigned: для signed overflow у C поведінка не визначена, і переносити цей висновок не можна.

### 7. Байти в пам'яті та endianness (memory.c)

Прогноз: варіант B (78 56 34 12).

```
value = 0x12345678

Address             Value
0x7ffc2dc56cc8  0x78
0x7ffc2dc56cc9  0x56
0x7ffc2dc56cca  0x34
0x7ffc2dc56ccb  0x12
```

- У якому напрямку змінюються адреси? Зростають на 1 від p[0] до p[3].
- Який байт за найменшою адресою? 0x78, молодший байт.
- Чому це little-endian? Молодший байт лежить за меншою адресою, старший (0x12) за більшою. У big-endian було б навпаки.
- Чи змінилося число 0x12345678? Ні, значення те саме. Змінився лише порядок розташування його байтів у пам'яті.

### 8. Одні біти, різні інтерпретації

| Інтерпретація | Значення |
|---|---|
| Binary | 01000001 |
| Hexadecimal | 0x41 |
| Unsigned decimal | 65 |
| ASCII character | A |

Чому комп'ютеру недостатньо знати лише біти? Послідовність бітів не містить інформації про те, чим вона є. Значення визначається типом, інтерпретацією та контекстом: ті самі 01000001 можуть бути числом 65, літерою A, частиною машинної інструкції або кольором пікселя.

### 9. Підсумкова програма (inspect.c)

```
Enter value (0-255): 65
Decimal:      65
Hexadecimal:  0x41
Binary:       01000001
Character:    A
```

### 10. Відповіді на контрольні питання

1. Біт це найменша одиниця інформації (0 або 1). Байт це 8 бітів.
2. n бітів дають 2^n різних значень.
3. 8-бітне unsigned: 0...255.
4. 8-бітне signed у two's complement: -128...+127.
5. Hex зручний, бо одна hex-цифра відповідає точно 4 бітам, тож двійкові дані (адреси, байти, регістри) записуються коротко й читаються легко.
6. 11111111 як uint8_t це 255, як int8_t це -1. Біти однакові, відрізняється інтерпретація.
7. Після 255 + 1 у uint8_t значення стає 0 (обертання за модулем 256).
8. Для символу A в пам'яті зберігається один байт 01000001 (число 65, код ASCII).
9. Endianness це порядок розташування байтів багатобайтового значення в пам'яті.
10. Досліджувана x86-64 система використовує little-endian.
11. sizeof(int) це розмір типу int у байтах на поточній платформі (тут 4).
12. Одні й ті самі біти можуть бути різними даними, бо значення визначається типом та інтерпретацією, а не самими бітами.

### 11. Підсумок

Експериментально встановлено: на Linux x86-64 int займає 4 байти, long та вказівник по 8. Те саме значення можна записати в десятковій, шістнадцятковій та двійковій формах. Біти набувають значення лише через тип: байт 11111111 це 255 для uint8_t і -1 для int8_t. Беззнаковий uint8_t при 255 + 1 обертається в 0. Символи зберігаються як числові коди (A = 65). Система використовує little-endian: байти 0x12345678 лежать у пам'яті як 78 56 34 12 за зростаючими адресами.

## Lab 2

**Від C до Assembly та машинного коду.** Код: `labs/lab02-assembly/`. Assembly отримано командами `gcc -Wall -Wextra -O0 -S -masm=intel` (Intel syntax), машинний код переглянуто через `objdump -d -M intel`.

### 1. Очікування до запуску

Питання лаби: що має зробити CPU для `int result = a + b;`? Моя відповідь до перегляду Assembly: отримати значення a, отримати значення b, додати значення, зберегти результат. Після перегляду Assembly це підтвердилось (див. розділ 2).

### 2. Arithmetic (arithmetic.c)

Програма вивела `Result: 12`. Assembly функції `main` (службові рядки прибрано):

```
mov  DWORD PTR -12[rbp], 5        ; a = 5
mov  DWORD PTR -8[rbp], 7         ; b = 7
mov  edx, DWORD PTR -12[rbp]      ; взяти a
mov  eax, DWORD PTR -8[rbp]       ; взяти b
add  eax, edx                     ; додати
mov  DWORD PTR -4[rbp], eax       ; зберегти в result
...
call printf@PLT
...
ret
```

- Чи кожному рядку C відповідає одна інструкція? Ні: `int result = a + b;` стало чотирма інструкціями.
- Чи видно змінні `a`, `b`, `result`? Ні, в Assembly лише місця в пам'яті (`-12[rbp]` тощо) і регістри.
- Приблизно 19 інструкцій у `main`.
- Додавання є: `add eax, edx`.

### 3. Арифметичні операції (operations.c)

Програма вивела `30`. У `calculate` аргументи приходять у регістрах `edi` (a) та `esi` (b), результат повертається в `eax`.

| C | Основна Assembly-інструкція |
|---|---|
| `a + b` | `add` |
| `a - b` | `sub` |
| `a * b` | `imul` |

Після зміни операції в C змінилась лише одна інструкція, що виконує обчислення. Збереження аргументів, запис у `result` і `ret` лишились однаковими.

### 4. if (condition.c)

Програма вивела `20`. Assembly функції `max_value`:

```
cmp  eax, DWORD PTR -8[rbp]   ; порівняти a з b
jle  .L2                      ; якщо a <= b, перейти в else
mov  eax, DWORD PTR -4[rbp]   ; return a
jmp  .L3
.L2:
mov  eax, DWORD PTR -8[rbp]   ; return b
.L3:
```

| C | Assembly |
|---|---|
| `if (a > b)` | `cmp` + `jle .L2` |
| `return a` | `mov eax, DWORD PTR -4[rbp]` |
| `else` | мітка `.L2:` |
| `return b` | `mov eax, DWORD PTR -8[rbp]` |

Інструкції `IF` у процесора немає. `cmp` порівнює значення й записує результат у прапорці, а умовний стрибок (`jle`, `jg`, `je`, `jne`) дивиться на прапорці й переходить на мітку або йде далі. Компілятор поставив протилежну умову (`jle`), бо стрибає в `else`, коли `a > b` хибне.

### 5. Цикл (loop.c)

Програма вивела `15`. У `sum_to`: `n` це `-20[rbp]`, `sum` це `-8[rbp]`, `i` це `-4[rbp]`.

```
mov  DWORD PTR -8[rbp], 0     ; sum = 0
mov  DWORD PTR -4[rbp], 1     ; i = 1
jmp  .L2
.L3:                          ; тіло циклу
mov  eax, DWORD PTR -4[rbp]
add  DWORD PTR -8[rbp], eax   ; sum += i
add  DWORD PTR -4[rbp], 1     ; i++
.L2:                          ; умова
mov  eax, DWORD PTR -4[rbp]
cmp  eax, DWORD PTR -20[rbp]  ; i <= n ?
jle  .L3                      ; так, повторити
```

- Порівняння виконує `cmp`, перехід `jle` (стрибок назад) і `jmp` (початковий перехід до умови).
- Поняття `for` в Assembly немає: цикл це порівняння, умовний стрибок назад і мітки.
- CPU знає, що цикл треба повторити, за прапорцями після `cmp`: якщо `i <= n`, `jle` переходить на тіло циклу, інакше виконання йде далі.

### 6. Виклик функції

У `main`:

```
mov  esi, 20            ; другий аргумент
mov  edi, 10            ; перший аргумент
call calculate          ; виклик
mov  DWORD PTR -4[rbp], eax   ; результат з eax -> value
```

Виклик `calculate` це `call calculate` у `main`, код функції починається з мітки `calculate:` і закінчується `ret`. Результат повертається в регістрі `eax`. Після `call` процесор повертається на інструкцію, що стоїть одразу після нього, бо `call` перед стрибком зберігає адресу повернення в стеку, а `ret` бере її звідти й стрибає назад. Стек докладно розглядається в наступній лабораторній.

### 7. Machine code (operations)

Фрагмент `objdump -d -M intel operations` для `calculate`:

```
115d:  01 d0        add  eax,edx
1151:  89 7d ec     mov  DWORD PTR [rbp-0x14],edi
1166:  c3           ret
```

| Address | Machine-code bytes | Assembly |
|---|---|---|
| 115d | `01 d0` | `add eax,edx` |
| 1151 | `89 7d ec` | `mov DWORD PTR [rbp-0x14],edi` |
| 1166 | `c3` | `ret` |

- У виконуваному файлі зберігається машинний код (байти), тексту Assembly там немає.
- `objdump` показує Assembly, бо це дизасемблер: перетворює байти назад у читабельний запис для людини.
- Ні, довжина інструкцій x86-64 різна (`ret` 1 байт, `add` 2, `mov` з пам'яттю 3, `mov` з константою 7).
- Людині зручніше читати Assembly, бо `add eax,edx` одразу говорить, що відбувається, а `01 d0` треба розшифровувати. Це два записи однієї інструкції.

### 8. Оптимізація (-O0 проти -O2)

Рядків у файлах: `operations_O0.s` 78, `operations_O2.s` 58 (багато однакових службових директив).

`calculate` з `-O2` складається з двох інструкцій перед `ret`:

```
lea  eax, [rdi+rsi]    ; a + b одним рядком
ret
```

`main` з `-O2` не містить ні `call calculate`, ні додавання: замість цього `mov edx, 30`, тобто результат пораховано під час компіляції (constant folding), а функцію вбудовано (inlining). Зникли також усі записи змінних у пам'ять і читання назад.

### 9. Прогноз компілятора (optimize.c)

Прогноз: варіант B (компілятор одразу поверне 30). Прогноз зроблено після того, як я вже бачив `mov edx, 30` в `main` з `-O2`, тому він не повністю незалежний.

```
-O0:  push rbp / mov rbp,rsp / mov eax, 30 / pop rbp / ret
-O2:  mov eax, 30 / ret
```

Прогноз підтвердився, причому навіть `-O0` одразу кладе 30: згортання констант виконується завжди. Різниця лише в службових рядках про стек. Компілятор має право замінити `10 + 20` на `30`, бо видима поведінка програми не змінюється (принцип as-if), а порахувати наперед виходить швидше.

### 10. Власна програма (analyze.c)

Функція `process(a, b)`: якщо `a > b`, `result = a - b`, інакше `result = a + b`; потім цикл із трьох ітерацій подвоює `result`. Для `process(10, 4)` вивід `48` (10 - 4 = 6, потім 12, 24, 48).

Знайдено в `objdump -d -M intel analyze`:

- арифметика: `sub` та `add`;
- порівняння: `cmp`;
- умовні стрибки: `jle` (if/else) і `jle` (цикл, стрибок назад);
- цикл: `.L5` тіло, `.L4` перевірка `cmp ..., 0x2` та `jle`;
- повернення: `mov eax, ...` і `ret`.

Множення `result * 2` компілятор реалізував зсувом вліво (`shl`, у тексті GCC `sal`), а не `imul`: зсув на 1 біт ліворуч це множення на 2.

| C | Assembly | Address | Machine-code bytes |
|---|---|---|---|
| `result = a - b;` | `sub eax,DWORD PTR [rbp-0x18]` | 1169 | `2b 45 e8` |
| `if (a > b)` | `cmp eax,DWORD PTR [rbp-0x18]` | 1161 | `3b 45 e8` |
| `result = result * 2;` | `shl DWORD PTR [rbp-0x8],1` | 1185 | `d1 65 f8` |

Байти `jle` (`1164: 7e 0b`): `7e` це команда стрибка, `0b` відстань у байтах; `0x1166 + 0x0b = 0x1171`, тобто адреса мітки `.L2`.

### 11. Відповіді на контрольні питання

1. ISA (Instruction Set Architecture) це набір інструкцій, який розуміє процесор, разом з регістрами й способами адресації. Тут x86-64.
2. CPU не може виконувати C, бо вміє виконувати лише машинні інструкції своєї ISA; C треба скомпілювати.
3. Assembly це текстовий запис інструкцій для людини, машинний код це самі байти, які виконує CPU. Це два представлення того самого.
4. `-S` зупиняє GCC після створення Assembly (без асемблювання й лінкування).
5. `-O0` вимикає оптимізацію, щоб Assembly був простим і близьким до C-коду.
6. Operand це значення, над яким працює інструкція: регістр, комірка пам'яті або константа (у `add eax, edx` операнди `eax` та `edx`).
7. `mov` копіює значення (між регістрами, пам'яттю й константами).
8. `cmp` порівнює два значення й записує результат у прапорці процесора, які потім перевіряє умовний стрибок.
9. `if` реалізується через `cmp` та умовний стрибок, що перестрибує потрібну гілку.
10. Цикл це порівняння, умовний стрибок назад і мітки.
11. `call` викликає функцію: зберігає адресу повернення й переходить до коду функції.
12. `ret` повертається з функції на збережену адресу повернення.
13. Одному рядку C може відповідати кілька інструкцій (`a + b` це завантаження, додавання, збереження), а інколи жодної (константи згортаються).
14. `objdump -d` дизасемблює виконуваний файл: показує адреси, байти машинного коду та відповідні інструкції.
15. `-O2` тримає значення в регістрах, вбудовує функції й згортає константи, тож код суттєво коротший.
16. Так: компілятор може видалити код, який не впливає на видиму поведінку програми (результат не використовується, гілка недосяжна, обчислення зроблене наперед), за принципом as-if.

### 12. Висновок

Процесор виконує не C, а машинні інструкції, і одному рядку C відповідає одна, кілька або жодної інструкції. Арифметика, `if` і цикли зводяться до простих операцій: `add`/`sub`/`imul`, `cmp` та стрибків. Аргументи функцій передаються в регістрах (`edi`, `esi`), результат повертається в `eax`. У виконуваному файлі зберігаються байти, а Assembly це їхній читабельний запис. Результат компіляції залежить від оптимізації: на `-O2` компілятор вбудовує функції й рахує константи наперед.

### Відповіді на контрольні питання

1. Препроцесинг, компіляція, асемблювання, лінкування. Результат: executable.
2. Preprocessor обробляє директиви `#` (`#include`, `#define`) і прибирає коментарі. Результат це C-текст (`.i`).
3. Compiler створює Assembly (`.s`) для конкретної ISA.
4. Assembler перетворює Assembly на машинний код і пакує його в object file (`.o`).
5. Object file містить машинний код, дані, таблицю символів і інформацію для relocation. Адреси ще не остаточні.
6. Linker об'єднує object-файли й бібліотеки, зіставляє символи з визначеннями, призначає адреси й створює executable.
7. `undefined reference` означає, що символ використано, але його визначення не знайдено (у мене `calculate`).
8. Symbol це ім'я функції або змінної в таблиці символів. `U` у `nm` означає символ, визначений деінде.
9. Header містить оголошення, які препроцесор підставляє в код. Library містить скомпільовану реалізацію, яку підключає лінкер (`printf` у `libc`).
10. ELF (Executable and Linkable Format) це формат object-файлів, виконуваних файлів і бібліотек у Linux.
11. `.text` містить машинний код програми (`add`, `main`).
12. `.rodata` містить константи лише для читання: рядкові літерали, `const`-дані (`"Result: %d\n"`, `message`).
13. `.data` містить ініціалізовані глобальні й static змінні та займає місце у файлі. `.bss` містить неініціалізовані (нульові) змінні, у файлі лише їх розмір.
14. `.bss` має тип NOBITS: у файлі зберігається лише розмір, нулі створює завантажувач. У моєму експерименті `bss` виросла на ~400 000 байтів, а файл на 40.
15. `ldd` показує динамічні бібліотеки, від яких залежить executable (`libc.so.6`, `ld-linux-x86-64.so.2`).
16. Executable це файл на диску, process це запущена програма в пам'яті з PID і станом. З одного файлу можна запустити багато процесів.
17. Локальні змінні концептуально лежать у стеку (у кадрі функції).
18. Heap потрібна для динамічної пам'яті (`malloc`/`free`), коли розмір або час життя даних відомі лише під час виконання.
19. Стек керується автоматично (кадр створюється при виклику й знищується при поверненні), він швидкий і обмежений за розміром. Купою керує програма (`malloc`/`free`), блок живе, доки його не звільнять. У моєму експерименті стек ріс до менших адрес.
20. Через ASLR система випадково зсуває початок програми, купу й стек при кожному запуску (у моїх трьох запусках адреси були різні).
21. Temporal locality: до даних, до яких щойно звертались, швидше за все звернуться знову (наприклад, лічильник циклу). Тому їх вигідно тримати в кеші. З теорії, в експериментах не перевірялось.
22. Spatial locality: після звернення до адреси швидше за все звернуться до сусідніх (наприклад, послідовний обхід масиву). Тому кеш завантажує цілі блоки (cache lines). З теорії, в експериментах не перевірялось.

### Висновок

Я пройшов увесь шлях `.c` → `.i` → `.s` → `.o` → ELF executable. Кожен етап дає окремий тип файлу, а зовнішні символи й бібліотеки підключає лише лінкер. У ELF код лежить у `.text`, константи в `.rodata`, ініціалізовані дані в `.data`, неініціалізовані в `.bss`, який майже не збільшує розмір файлу. Експерименти з адресами показали поділ процесу на код, дані, купу й стек та дію ASLR. Мій прогноз про напрямок росту стека не підтвердився: у моєму середовищі (x86-64) стек росте до менших адрес.
